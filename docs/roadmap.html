Data flow — assertion log to conclusion

A command runs through the pure decide (no clock, no ids, no I/O). The non-deterministic inputs are minted once in Session. Events are the append-only assertion layer; projections are the rebuildable conclusion layer. A plugin is just another operator — an AgentKind::Software claim, audited identically to a human's.

Phase 1 spikes in detail

Spike A — Cross-aggregate model done

Add minimal Event, Place, Source, Citation aggregates — enough to prove the multi-aggregate machinery and to give EventContext.citations something real to point at.

  • Cross-aggregate references as ids in the payload (ADR 0002 self-contained events).
  • Person↔Event participation; Citation→Source link.
  • Projection-based invariant checks — UnknownPlace, UnknownSource (the §9 "aggregate tax": checked against possibly-lagging projections, not transactionally).
  • i18n moved up: first date-bearing aggregate, so localized GenealogicalDate via ICU4X + Fluent terms; the second-locale completeness checker lands now (two locales exist).

Kills: "does the multi-aggregate reference + invariant pattern actually hold?"

Cross-aggregate decide with a projection-backed check (illustrative):

// genealogy-core::event::decide — the cross-aggregate invariant the spike must prove.
// `known_places` is a snapshot of the Place projection, passed in by the app layer —
// the decision core stays pure; the "aggregate tax" is a read, not a transaction.
pub fn decide(state: &EventState, cmd: EventCommand, known_places: &PlaceIndex)
    -> Result<Vec<EventEvent>, EventError> {
    match cmd {
        EventCommand::LinkPlace { event_id, place_id, meta } => {
            if !known_places.contains(&place_id) {
                return Err(EventError::UnknownPlace(place_id)); // §10.1
            }
            Ok(vec![EventEvent::PlaceLinked { event_id, place_id, meta }])
        }
        // … SetEventType, AssertDate, AddParticipantRole, AddCitation
    }
}

Spike B — Event evolution + projection rebuild done

Prove schema evolution and read-model rebuild while the log is still tiny.

Kills: "can we evolve the event schema and rebuild projections?"

// ADR 0004 §4: variant-name + version, internally-tagged JSON, additive only.
// A v1 event must still decode after v2 ships — the upcaster fills new fields.
fn upcast(raw: StoredEvent) -> NameAsserted {
    match raw.version {
        "1" => NameAsserted { // v1 had no `language` field
            name: raw.decode::<NameV1>().into(),
            language: None,                     // additive default
        },
        "2" => raw.decode::<NameAsserted>(),
        other => unreachable_version(other), // typed error, never panic
    }
}

Spike C — Plugin host (WASM) + GEDCOM import/export plugin done

The single biggest technical unknown. One slice proves the host, the WIT/DTO boundary, Software-agent provenance, and a real import/export round-trip.

Kills: "does the WASM component plugin host work end-to-end?"

// host.wit — ONE versioned host world; plugins pin the interface, not the app (ADR 0007).
package genealogy:host@0.1.0;

interface use-cases {
    // Plugins see the same frontend-neutral DTOs as the UI — no cqrs-es / sqlx leakage.
    record person-dto { human-id: string, display-name: string, sex: string }
    create-person: func(given: string, surname: string) -> result<string, app-error>;
    add-child:     func(family: string, person: string) -> result<_, app-error>;
}

world import-plugin {           // deny-by-default: only what the bundle requests
    import use-cases;            // command capability
    import wasi:filesystem/preopens; // one preopened dir — the file to import
    export run: func(input: string) -> result<import-summary, plugin-error>;
}

Every claim the plugin makes is audited as a non-human operator:

EventContext {
    operator: Agent { kind: AgentKind::Software { name: "gedcom-import", version: "0.1.0" }, .. },
    confidence: Confidence::Low,   // machine claim enters the evidence layer, not conclusions
    rationale: Some("imported from INDI @I42@"), ..
}

Phase 13 — Beyond 1.0: server backend + web frontend

Direction set by the project owner; sketched so the 1.0 architecture stays compatible — not scheduled. After 1.0 the app gains a third deployment shape alongside today's embedded (workspace = local directory + database). All three pieces are additive: the embedded build keeps working unchanged.

Backend server. Run genealogy-app as a long-lived process owning workspaces, exposing the existing use-cases + DTOs over the network — a new frontend over the same coordination layer (ADR 0006), not a re-implementation. Session stays the impure boundary; the operator now resolves from an authenticated principal (the direction ADR 0005 already fixed).
Web frontend. A browser client reusing genealogy-ui view-models and intents unchanged — ADR 0008's promise that a second renderer reuses genealogy-ui as-is. A new renderer parallel to genealogy-ui-dioxus (Dioxus already targets web).
Server-connected workspaces. init/the GUI can register a workspace pointing at a server endpoint instead of a local database_url; the CLI/GUI become clients. The PersistedEventRepository/Store seam (ADR 0002) — or a use-case transport above it — carries calls to the server.
Config storage (builds on Phase 7). The split into workspace-functionality / operator / client-presentation scopes and the ConfigStore seam landed in Phase 7. The server adds the seam's database backend so the operator and client/presentation scopes persist per authenticated principal server-side and a browser client carries no local config file. Embedded keeps the file backend.

Editing patterns

Where a record's inputs render — inline on the row, in a side panel, or in an attach dialog — picked by how much you're changing. These are containers for the one editing model (read-first, whole-record draft, Save appends to the audit trail) defined in Record editing; documented here so every screen behaves the same way, and so we never reproduce Gramps' dead-ends where a missing related record forces you to cancel and start over.

a · Inline edit — for ≤3 simple fields

A fact row turns its values into inputs in place — the fast way into the record's edit session for a quick correction on a row you're already looking at. Edits go to the draft; Save appends to the audit trail, Esc reverts the field.

b · Side panel — for complex edits

When an edit has 6+ fields, nested sub-records, or needs a citation attached, a slide-in panel keeps you in context with the record still visible behind it.

It is modal, so visible is all the record behind it is: while the panel is open the pane it covers and every shell region around it — rail, Explorer, top bar, tabstrip, status bar, notice layer, skip link — carry inert and aria-hidden, which closes the pointer, Tab and assistive-technology paths together (ARIA APG modal pattern). The panel is rendered as the pane's sibling, not inside it: inert is inherited and no descendant can undo it, so a panel within the inerted subtree would disable itself. Closing the panel lifts it all again and returns focus to the control that opened it.

c · Attach-related dialog — with inline “create new”

Picking an existing related record (a citation, a place, a person) always offers a + New path right in the dialog. You never hit the Gramps dead-end where the record you need doesn’t exist yet and you must cancel out to create it first. A “+ New” child is a deferred draft — it persists only when you save the root record.

Every dialog sits on the .overlay layer behind a .modal-scrim click-away, traps Tab between its own controls, and returns focus to whatever opened it — see design-system.

The same find-or-create appears in-form as a record picker (record-editing §6b) — the create-form variant, where the result list is a dropdown over the fields below it rather than a dialog, and “+ New” opens a nested .draft-card rather than a modal. The side-panel and attach pickers are find-or-create the same way every other picker is (issue #314): “+ New …” opens a nested .draft-card seeded with whatever you typed, and nothing is written until the panel’s own Save, which commits create-then-attach, in that order. A failed create writes nothing and leaves the card exactly as typed; a failed attach leaves the just-created record in place and collapses the card to a picked chip, so a retried Save only re-attaches — it never creates the record twice. A picker reloads its options after every create, edit or undo, so a record created elsewhere while the panel stays open is pickable in it — no reopen (record-editing §6).

Links that carry a role pick it in the same dialog. When the attachment is a typed relationship — a person joining an event (ParticipantRole), a child joining a family (ChildParentRelationship per parent) — the dialog adds the role picker next to the selection, so the link is complete in one step:

d · Rules of thumb

These pick the container for the inputs. The editing model — read-first, a whole-record draft, per-field Reset, and Save that appends to the audit trail — is the same in all three; see Record editing.

modalUse a modal for a focused action of ≤5 fields (attach, confirm, quick create).
side panelUse a side panel for 6+ fields or anything nested — keep the record visible behind it.
inlineUse inline edit for ≤3 simple fields on a row you’re already looking at.
neverNever nest modals. A dialog that needs another record offers inline + New instead.
alwaysAlways label icon buttons (tooltip + aria-label). No mystery glyphs.

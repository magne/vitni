Record editing — create & edit one record

Every aggregate (Person, Family, Event, Place, …) is created and edited the same way: a record is read-first; one Edit turns the whole record into inputs; edits accumulate in an in-memory draft; nothing is written until you Save. This page defines that mode model and the create flow. For where the inputs render (inline row, side panel, attach dialog) see Editing patterns; for the keys, Keyboard & accessibility.

One model, two entry points. Create and edit share one form — create just starts from an empty draft. Read mode and edit mode occupy the same layout so switching causes no text movement. This supersedes the pattern where a record shows always-live inputs with no Save/Cancel; a record is a value you read until you choose to edit it, and Save is what appends to the event-sourced audit trail.

1 · View mode (read-first)

The default. Fields are read text with their evidence cues (confidence, source / no-source). Every field is keyboard-focusable, but only one is in the tab order (a roving tabindex); arrows move between them, and the whole record has a single Edit button.

2 · Entering edit mode — the whole record

Clicking Edit (or e / F2 / double-click on a focused field) turns the entire record into inputs and focuses the first field — or the field you triggered it from. There is only one edit mode; the per-field shortcuts are just a fast way into it. Edit is replaced by Save + Cancel.

3 · No reflow: read ≈ edit

The read value and its input occupy the same box — same padding, height, and baseline — so toggling a field between modes moves no text. A read value is an input with a transparent border.

Locked (non-editable) fields keep the read box and, in edit mode, render as a disabled input rather than jumping to text.

4 · Draft state, per-field commit & Reset

Committing a field (Enter, or Tab/⇧Tab to the next/prev field) updates the in-memory draft only — nothing is persisted. Esc restores that field's original value and leaves its edit. A field whose draft differs from its original is modified: the control is tinted with the accent wash and gains an inline reset icon at its right edge (left of any dropdown arrow or number spinner), shown only while the field is changed.

5 · Save, Cancel & the audit trail

A record is in an edit session the moment any field differs from its original. During a session the record shows Save and Cancel and hides Edit.

SaveValidates every modified field, then commits the changed assertions to the append-only audit trail — one event per changed assertion (who / when / why), never a mutation. Changing an existing value emits AssertionSuperseded referencing the prior claim by its AssertionId; the old claim stays in History. Returns to view mode and confirms with a polite toast.
CancelRestores every field to its original value, ends the session, and returns focus to the field that had it.
disabledSave stays disabled until the record is dirty and valid — the state never looks active when there is nothing to save.

Confirmation is an aria-live="polite" region; it announces without stealing focus.

5a · Leaving with unsaved changes

An edit session is unsaved work, whether the record is new (§6) or already stored. Both block a close: ⌘W (and the tab's ✕) and ⌘Q raise a confirm rather than discarding the draft silently. The record's tab also carries an ● unsaved marker (see App shell), so pending work is visible without opening the tab.

What counts is typed-in work, not the tab's kind: a create form nobody has typed into holds nothing, so ⌘W (or its ✕) closes it with no dialog, it carries no ● marker, and it does not make ⌘Q claim there is unsaved work. The first thing typed into it makes it a draft with work, and everything below applies; backspacing over that again makes it closable without a prompt once more.

The confirm names what is at stake, and the wording differs by case — a draft is not saved yet, a stored record has unsaved changes. Saying the second is unsaved would be untrue: the record exists, only the edits are at risk.

Three actions, so keeping the work is one click rather than a detour: Save (primary) commits the record and then closes the tab, Discard closes it and loses the work, Cancel backs out. The shell cannot save on its own — save is per-screen and shaped per aggregate — so Save activates the record's tab and runs that screen's Save, the same commit the header button fires.

An in-progress edit is parked per record rather than held by the open editor. Only the active tab's pane is mounted, so switching tabs or opening another record would otherwise discard the draft: instead the buffer — the draft, the committed values it is diffed against, and the provenance filled in so far (§5b) — is kept in shell state and handed back when the record comes forward again, still in edit mode. Several records can be mid-edit at once, and every one of their tabs carries the ● marker, not just the active one.

5b · Provenance on Save — who · when · why

Every assertion carries an EventContext: operator, time, rationale, confidence, backing citations, and an optional evidence analysis. Confidence is captured inline per field (§2); the rest is captured in a provenance block shown above Save/Cancel while a record is dirty. Everything except confidence is optional — but the slot is always there, because History displays the "why" and the prov popover displays the citations, and neither can be shown if it was never collected.

The block's citations picker offers “+ New citation”, and unlike the nested drafts of §6b that card commits as soon as you press Add — the citation (and a source created with it) persists even if the surrounding form is cancelled. Because it is a create like any other, it updates the rail counts, the Explorer list and every open picker, so the citation it just made is immediately attachable from the picker beside it.

6 · Create = a throwaway draft, or several

+ New (⌘N) opens the same form on an empty draft that is never stored. Same validation, dirty-tracking, and Save/Cancel as edit — the only difference is create starts empty and Save creates the record instead of updating it. Every ⌘N starts another draft, of the same category or a different one: two new people can be sketched side by side, each with its own form, its own caret and its own buffer, and each tab names itself by what has been typed into it. Cancel and Save address the draft they belong to. Cancel discards the draft; nothing is written. On Save the draft tab becomes the stored record in place, and the Explorer list beside it gains the new row and the rail's count badge updates — no manual refresh. The same holds for every record picker still open elsewhere (§6b, and the find-or-create pickers of edit-patterns §c) and for the open command palette: each reloads its options after any create, edit or undo, so a record created while it stays open is pickable in it without reopening the form.

6b · Nested drafts — cascading create

A field that links to another record uses a record picker: type to search, pick an existing record, or press the picker's “+ New …” row to create one inline, seeded with whatever you typed. A “+ New” row opens a .draft-card — a raised, bordered, offset sub-form named for what it creates — nested inside its container, and, inside a create form, recursively (a new Citation card can hold a new Source card). Each card carries a draft badge and a ✕ that discards just that child (its subtree drops; the rest of the draft stays).

This same nested-draft mechanism appears in exactly three containers: a record's own create form (recursive, as above — the whole tree commits with the root's Save), the provenance block's own “+ New citation” card, and an attach side panel's link field (below). No new aggregate persists until the container's own Save commits it — with two deliberate exceptions, both for the same reason: the provenance block's citation card and the Research note Subjects field commit on Add rather than on any record's Save, because neither sits inside one. A Research note's subjects are a flat list of ids with nowhere to hold an uncommitted draft, so a new subject is created as it is added, exactly as a new citation is.

Validation runs when a field is left, and again before Save. An invalid field stays modified, shows an inline message, and gets aria-invalid="true"; Save is blocked with focus moved to the first invalid field.

8 · Record scalars vs related collections

Record-level Edit governs the record's own scalar fields. A record's related collections (a Note's translations, a DNA test's haplogroups, a Person's names) stay as tables whose rows carry their own per-row Edit/Retract/+ Add — each row is a sub-record edited on its own terms, not folded into the whole-record draft. Because rows are assertions, the row actions map onto the correction verbs: Edit emits AssertionSuperseded (a new claim referencing the old one by its AssertionId) and Retract emits AssertionRetracted — the row disappears from the conclusion view but stays in History. Nothing is ever deleted.

A record's privacy restrictions are scalars like any other, so they are edited the same way: the sticky header only displays the kinds in force (inert .resn-static pills, and nothing at all when the record is unrestricted), while the Restrictions row in the record card is the control — live toggles in edit mode over all three kinds. A toggle writes the draft, nothing else: it makes the record dirty, brings up the provenance block of §5b, and the change is committed by the record's own Save carrying that reason and its citations. No restriction changes on click.

A few collections carry a Remove verb alongside Retract — the Family Children tab is the case in point. Remove is not a correction: it emits ChildRemoved, recording that a membership which once held has ended, and the claim that added the child keeps standing. Retract says that claim was a mistake in the first place. Both are logged; only the meaning differs, so the two never share a button.

Retract, Detach and the Tags tab's Untag (× on a tag chip) all open the same side panel before anything is written: it names what is being removed, takes an optional reason — the same field as §5b, recorded in History with the operator and the time — and confirms with that one verb (Retract assertion · Detach · Remove tag). The untag panel names the tag, never its UUID (data-model §9). A removal is therefore as explainable as an edit; none of the three is a bare click.

Every collection tab is framed the same way, in three parts: the tab's explanation (.section-note), then a right-aligned .tab-actions bar holding a single button, then the tab's own table or gallery. The explanation comes first because it says what pressing that button asserts, and it is emitted outside the tab's body, so it survives the empty state — the moment a new operator has nothing else to infer the tab's meaning from. All three sit on one --sp-4 step.

The six tabs every aggregate renders the same way (Citations, Media, Notes, Tags, Addresses, History) are explained by the frame itself, once, rather than per screen; a tab a screen owns alone (Names, Facts, Segments) carries no explanation from the frame, because a note there would be a claim about that one entity rather than the vocabulary all 13 aggregates share. The button's verb is drawn from a closed set, never a free string, so a tab can never fall back to a generic "Save": Attach references an existing record (a citation, a media object, a note), Add creates a sub-record the tab itself owns (a name, a fact, a DNA segment), and Link creates a bidirectional association between two existing records (a family's linked event). The frame is the only place in a screen that emits .tab-actions — a read-only tab (History) renders its explanation and its body with no bar between them.

A record's History tab collapses a run of consecutive changes from the same software agent — an import, typically — into one row, so a bulk import reads as a single line rather than N. That row names the run by its origin (Imported from gedcom-import), never by a count of records: the count on one record's own history is of assertions on that single record, not of distinct records imported, so the Dashboard's N records imported wording — its own activity-feed phrase for the same run, by record count — does not belong here. The collapsed row is stamped from the run's newest entry, so it still carries an ↩ Undo control: ⌘Z retracts that assertion rather than skipping past the whole run to an older entry behind it.

Every tab that lists records attached to (or referencing) this record renders one shape: a table.tbl whose first column is a link opening that record, then the columns that tab is about, then the row's actions. That covers Citations, Notes, a research note's Subjects, the reverse-lookup tabs (a note's References, a media object's Used by, the Research notes written about a record) — so an attached record can always be opened from the record that references it, and a reverse lookup is a way back rather than a dead list. The Media gallery is the one deliberate exception: a thumbnail is the point of that tab, not a row. A reverse-lookup table carries no row actions at all — the reference is asserted on the other record, so it is detached there.
